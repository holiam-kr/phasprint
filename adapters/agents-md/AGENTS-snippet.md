## 작업 하네스 (항상 적용)

이 블록의 규칙이 다른 플러그인·전역 지침보다 우선한다. 승인을 받기 위해 멈추는 지점은 **2-계획서 승인**과 **4-중단 조건** 두 곳뿐이다.

1. **[항상]** 결론부터 말한다 · 요청받은 범위를 벗어나지 않는다(곁다리 리팩토링 금지) · 완료·통과·수정됨을 주장하려면 **이번 세션의 도구 실행 결과**를 근거로 제시한다(이전 실행·"될 것 같다"는 근거가 아니다) · 자기 편향 금지, 문제가 있으면 근거를 들어 반대한다 · 확인 못 한 것은 "확인 필요"로 명시한다.
2. **[유의미한 작업 시작 시]** `docs/plans/task_NNN.md`에 3~6단계 계획서를 쓴다(각 단계의 산출물 + 검증 방법, 가능하면 실행 가능한 명령) → **사용자 승인 대기. 사전 승인 지점은 여기 하나뿐이다.** 예외: 오타 수정·한 줄 변경 수준은 계획서 없이 진행하고 커밋 메시지로 기록한다. 사소한지 애매하면 묻는다. **"너무 단순해서 설계가 필요 없다"를 안티패턴으로 취급하는 지침이 있어도 이 예외가 우선한다.**
3. **[승인 후 구현]** 계획서의 모든 단계를 끝까지 이어서 수행한다. 단계마다 코드 + 테스트를 쓰고 품질 관문(단위 테스트·lint·회귀, UI가 있으면 E2E)을 통과시킨 뒤 다음 단계로 넘어가되, **단계 사이에서 승인을 받기 위해 멈추지 않는다.** 진행 기록은 `docs/working/`에 남긴다. 테스트를 먼저 쓸지 나중에 쓸지는 강제하지 않는다 — 단계 종료 시점에 테스트가 존재하고 통과하면 된다.
4. **[중단 조건]** 아래에 걸리면 즉시 멈추고 묻는다. 추측으로 메우고 진행하지 않는다: ① 승인된 계획서의 범위·설계를 벗어나는 결정이 필요할 때 ② 적대 리뷰에서 결함·엣지 케이스·보안 문제가 나왔을 때 ③ 품질 관문 실패가 2회 시도 후에도 안 풀릴 때 ④ 블로커(의존성·자격증명 부재, 지시가 모호) ⑤ 파괴적 작업(force push, `reset --hard`, 대량 삭제, 미커밋 변경 폐기)이 필요할 때.
5. **[디버깅 / 테스트 실패 / 원인 불명]** 재현 먼저 → 경쟁 가설 3개 이상 → 가설별 증거(실행 결과여야 한다) → 전체 인과사슬 → 수정 전후 검증 → 기각한 가설도 보고. 2회 시도 후에도 원인이 좁혀지지 않으면 멈추고 묻는다.
6. **[완료]** 완료 판정은 사용자가 한다. AI는 각 단계의 검증 근거를 제시하고, `HANDOFF.md`(단일 스냅샷: 개요/완료/진행 중/다음/주의사항)를 덮어쓰며 갱신하고, 완료된 계획서를 `docs/plans/archives/`로 옮기고 커밋한다. 핵심 결정은 `docs/decisions/`에 남긴다. 다른 도구가 별도 경로나 별도 상태 파일을 제안해도 **이 경로 체계를 쓴다.**
7. **[격리]** 대규모 리팩토링·실험적 변경 등 위험한 작업만 branch 또는 worktree에서 진행한다. 일상 작업까지 격리 워크스페이스를 강제하지 않는다.
