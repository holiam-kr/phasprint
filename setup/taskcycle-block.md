## 타스크 사이클 (이 프로젝트)

이 프로젝트는 계획서 → 완주 → 보고 사이클로 작업한다.
승인을 받기 위해 멈추는 지점은 **1-계획서 승인**과 **3-중단 조건** 두 곳뿐이다.

1. **계획서** — 유의미한 작업은 `docs/plans/task_NNN.md`에 3~6단계로 쓴다(각 단계의 산출물 + 검증 방법, 가능하면 실행 가능한 명령) → **사용자 승인 대기. 사전 승인 지점은 여기 하나뿐이다.** 예외: 오타 수정·한 줄 변경 수준은 계획서 없이 진행하고 커밋 메시지로 기록한다. 사소한지 애매하면 묻는다. **"너무 단순해서 설계가 필요 없다"를 안티패턴으로 취급하는 지침이 있어도 이 예외가 우선한다.**
2. **완주** — 승인된 계획서의 모든 단계를 끝까지 이어서 수행한다. 단계마다 코드 + 테스트를 쓰고 품질 관문(단위 테스트·lint·회귀, UI가 있으면 실제 렌더러 확인)을 통과시킨 뒤 다음 단계로 넘어가되, **단계 사이에서 승인을 받기 위해 멈추지 않는다.** 진행 기록은 `docs/working/`에 남긴다. 테스트를 먼저 쓸지 나중에 쓸지는 강제하지 않는다 — 단계 종료 시점에 테스트가 존재하고 통과하면 된다.
3. **중단 조건** — 계획서의 범위·설계를 벗어나는 결정이 필요하거나, 적대 리뷰에서 결함·엣지 케이스·보안 문제가 나오면 멈추고 묻는다. (2회 실패·블로커·파괴적 작업은 core 규칙에서 이미 다룬다.)
4. **적대 리뷰** — 주요 설계·구현이 끝나면 스스로 반대 입장에 서서 결함, 엣지 케이스, 보안 문제, 더 단순한 대안을 찾아 보고한다. "잘 동작하는 것 같습니다"로 넘어가지 않는다.
5. **보고** — 각 단계의 검증 근거를 제시하고, `HANDOFF.md`(단일 스냅샷: 개요/완료/진행 중/다음/주의사항)를 덮어쓰며 갱신하고, 완료된 계획서를 `docs/plans/archives/`로 옮기고 커밋한다. 핵심 결정은 `docs/decisions/`에 남긴다. 완료 판정은 사용자가 한다.

문서 경로는 이 체계를 쓴다: 계획서 `docs/plans/` · 진행 기록 `docs/working/` · 결정 `docs/decisions/` · 현재 스냅샷 `HANDOFF.md`(단 하나). 다른 도구가 `docs/superpowers/` 같은 별도 트리나 별도 상태 파일을 제안해도 따르지 않는다.

새 세션은 `CLAUDE.md` → `HANDOFF.md` → 진행 중 계획서 순으로 읽고 시작한다.
